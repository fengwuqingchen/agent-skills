# Plan 跨5小时额度窗口执行

## 适用条件

仅在真实账户读数确认存在5小时（300分钟）额度窗口，且用户明确需要跨限额续跑时使用。账号无5h限额（包括用户已确认无需此限制的Pro账号）时，不启动本skill，不建立额度唤醒日程，直接执行已授权任务。不要仅凭套餐名称推断限额；真实读数与用户明确说明优先。

目标是交付已验收的 plan，并避开用户实际使用电脑的时间。**任务未完成且仍在允许的执行窗口、有额度、有可执行工作时，必须继续调用工具推进，不允许以进度汇报、建议“下一步”或“要不要继续”结束。** 用额度做有用工作，不为了耗尽 token 扩大范围或重复已通过的检查。

## 启动协议：先让中断可恢复，再开始长任务

1. 读取用户指定 plan、项目约束和 Git 状态，定义可核查的完成条件。延续现有任务，不把修订/状态提问当作取消原任务。不擅自创建新聊天、改模型或并行代理。
2. 将用户电脑使用时段解析为带日期、时区的绝对区间；优先用户/客户端时区，默认 Asia/Shanghai。晚 7–12 点解释为 19:00–次日 00:00；不把 00:00 当成当日零点。缺日期且有唯一合理的下个时段可陈述假设；确实歧义时及早询问，继续不依赖答案的准备。
   - 用户给出“本周周一到周四”等模式时，将本次授权内每个日期展开为 `protected_intervals`，不能只保留最近一天，也不能擅自扩成永久偏好。
   - 其余时间均为候选执行时间，包括凌晨、深夜、周末。用户说“现在不用了，继续”即撤销当前占用假设，刷新额度后立即工作，不等到白天或下一次定时唤醒；将下一次真正使用时段作为停工边界。
3. 调用 `get_usage_limits`（工具名通过工具发现解析），优先 `rateLimitsByLimitId`；根据 limitId、模型、窗口分钟数选择实际约束，不能把 primary 固定当成 5h、secondary 固定当成周。`usedPercent` 是已用，未知不是零。保存精简读数，不保存 accountId/凭据。实际重置时间优先于“上次运行 +5h”。
4. 建立 `work/plan-quota-runner/<task-id>/state.json` 和 `checkpoint.md`。先保存任务 ID、plan/项目绝对路径、完成标准、用户使用区间、执行停工边界、额度策略、下一项具体工作和证据路径。多个任务不得共用状态文件。
5. 在当前聊天建立或更新唯一 heartbeat，**在可能触限前创建并核实**，不能等耗尽后再试。只通过 `automation_update`，不手写 automation.toml、不绕到 cron/CLI/API key。调用本 skill 并授权跨窗口执行，包含为本任务设续跑的授权；仅创建/编辑本 skill 本身不代表启动任何项目任务。
6. 核对工具返回的 automation ID、ACTIVE 状态、时区及实际下次执行时间，并写入状态。不可声称只凭成功返回就已验证未来会被唤醒。排程规则、恢复提示词见 [续跑协议](references/continuation.md)。如果环境不能可靠表达所需时间，直说调度缺口，完成可执行工作，不伪造保障。
7. 调用时向用户明确列出本次已设置的全部具体唤醒时间（年月日、时分、时区），说明何时会发送通知、何时仅静默执行；不能只说“稍后”“每隔几小时”或 every。优先固定、有限的日期时间点；长任务可先安排最近一批，明确本批覆盖范围，随后按真实额度重排并告知变更。区分计划唤醒与保证送达，工具未返回 next_run 时如实说明。另列任务终点、实际使用时段和停止边界，随后继续实施。

用户要求清空本聊天日程时，先盘点 target_thread_id，仅通过 automation_update 删除本聊天的全部既有日程（含暂停项），核实删除后重新规划；不触碰其他聊天，不用“暂停后继续复用”代替清空。保存删除记录及新日程映射。

## 用户使用时段与额度（当前默认策略）

- 只在用户实际使用电脑的区间 `[S,E)` 停止任务和模型唤醒，不提前五小时停工，不设置13:45等留额边界。其余时间包括夜间均可执行。即使当前额度窗口跨越使用时段，也可以工作到S；选择能在S之前完成/安全中断的增量，长操作提前保存检查点。
- 用户给出的重复使用模式按日期和时区展开。旧“取消留额”不等于取消用户使用时段；保护的是时间，不是周额度。仅用户明确撤销某次使用时段时才移除该区间。
- 空闲时不预留周额度、不使用16%/18%/34%等经验比例或下一操作估计作为提前停工条件。真实额度允许且有工作就继续，直到真实触限、用户使用开始、明确截止或真实阻塞。
- 允许跨周使用自动刷新的额度。刷新后核对真实读数并继续；周用量下降或reset边界改变不单独构成暂停/再次求授权理由。记录变化，不凭读数猜测原因。授权截止独立于周reset：保留用户明确截止；未给截止时以完成或用户停止为终点，排程仍按有限批次更新。
- 仅在用户明确允许使用重置卡时，才可在接近耗尽时消费卡。默认当任一实际窗口已用>=95%或普通使用因额度被拒时，若有未过期卡且当前不在使用时段，可使用一张；先保存检查点、查询可用卡和作用范围，通过官方工具或已验证的应用UI操作，随后重新读真实额度并记录卡数/结果。重置卡授权不包括购买额度、切换账户或付费API。调用skill本身不能替无授权用户消费卡。
- 重置只做一次在途操作。失败/响应不明先复查卡状态和额度，不盲目连用卡；复查无恢复则等自然reset，不消耗第二张。没有可用入口或卡时不得虚称重置，照常按自然reset续跑。保护时段内不为重置卡而唤醒。
- 真实触限且未通过重置恢复时，按最新reset后至少2分钟安排续跑；多个窗口同时耗尽取最晚reset。若落在用户使用时段内，移至该时段结束后。刷新后额度可用则无需再等旧reset。
- `scripts/quota_guard.py`只做确定性判断，不查询账户、不消费卡、不创建日程。输出WORK只允许当前有界增量；输出RESET_CREDIT要求执行者核实并实际操作，不能当作额度已恢复。

## 执行纪律：不允许“没完成、没触限、无理由收工”

- 将 plan 保持为带验收条件的工作清单；一次处理一个可验证增量，完成后立即推进下一个。阶段完成、上下文压缩、到了整点、已经花了很多 token，都不是结束理由。
- 优先处理关键路径与可用环境；遇到测试/类型/构建失败先定位修复，不靠删测试、缩小承诺范围或让用户明天再说来结束。对失败恢复重试；相同失败重复时换诊断或方法，不空转。
- 每个可恢复增量完成后更新检查点；至少每 15 分钟、长命令前、可能触限前额外更新。包括已改文件、命令/结果、尚未验收项、当前子进程与安全恢复方式、下一条具体命令。写入用临时文件后原子替换，先落盘再汇报。
- 每个阶段/大批工具操作后以及接近使用时段边界时刷新额度；临近边界将操作切小。必须安排并在执行中遵守停止时刻，不能只靠下次 heartbeat 停止当前轮。任务跨上下文压缩后先读状态，核对现场，不重新执行已经完成的迁移/外部动作。
- 跑着的当前轮负责推进；heartbeat 不是用来给仍在运行的聊天重复派单。复用同一任务状态，检查进程/未结束操作，禁止第二份迁移、重复写入和覆盖用户新改动。RUNNING只是上次检查点状态，不是仍在执行的证据；需核对当前线程与登记的命令/session，已结束操作或过期标记不能让之后整夜都被误判为“仍在运行”而跳过。不要建立无限循环/后台模型进程来掩盖当前回合已结束。
- 额度充足时，最终回答前强制自检：清单是否全验收？若否，是否确有额度耗尽、用户使用时段、用户停止/截止、权限或外部依赖阻塞？**都不是，就不得发 final，继续实际工作。** 记录任意主动结束理由，便于下一轮审计。

## 四种明确状态

| 状态 | 必须执行的行为 |
|---|---|
| RUNNING：未完成且允许继续 | 当前轮持续工具工作，不以汇报结束 |
| WAIT_QUOTA：额度实际耗尽/平台已拒绝 | 读取最近落盘检查点；按真实 reset+缓冲设下一轮；恢复时立即续做，不只报告额度 |
| RESERVED：进入用户实际使用时段/授权截止 | 检查点写明未完成与恢复条件，确保本任务无保护区内唤醒；使用结束后在授权期限内自动继续；允许自动刷新后的跨周额度 |
| DONE：所有要求与必要验收都有证据 | 首次交付结果；停止任务自动化。若一个已排队续跑仍到达且无新任务，仅输出 `已完成`，不扩展工作、不重跑验收 |

真实权限拒绝、机器离线或外部依赖故障不能伪装成上述已完成。先做可行替代及独立工作；确实无路可走时记入 BLOCKED，说明具体待用户动作，仅通知一次。恢复时重试适量并核对新证据。skill 不覆盖平台权限规则，也不能保证机器离线仍执行；不能为了“只允许两种 case”掩盖真实故障。

## 完成判定与通知

DONE 必须同时满足：plan 每项有实现/交付去向、必要验收实际通过、没有未解决的关键失败、证据可定位、停工/清理工作已完成。测试未执行或部分完成必须如实标注，不能将它们按全通过验收。

长任务用简洁 commentary 持续报告事实，不能用固定“继续中”替代工具工作。自动恢复时无变化/额度未恢复保持安静；只有完成、真实阻塞或需要用户操作时通知。未完成时不写“已完成”。已经完成不为了用满额度继续造工作。

启动时说明必要的本机前提：电脑开机、桌面应用运行、项目可访问。官方机制与经验预算的区别见 [依据](references/continuation.md#依据与限制)。不要把“已创建 skill/已设排程”说成“已经保证明天交付”。


## 调度故障核验与换窗缓冲

- 2026-10-28实测：含`DTSTART;TZID=Asia/Shanghai`的00:30配置虽然ACTIVE，调度数据库却登记名义08:30，last_run为空且无运行记录。不能把TOML与工具成功返回视为实际时区验证；这是已观察到的8小时偏差，不可推测为用户睡眠或额度故障。
- 优先将固定节点转为显式UTC（带Z）提交工具，再核对实际next_run_nominal_at与next_run_at换算后的用户时间。可只读检查本机codex-dev.db的automations/automation_runs并限于本任务字段；不得写数据库或手改TOML绕过工具。查不到实际调度字段时明确未验证，不保证唤醒。
- 每次换新额度窗口，续跑节点必须不早于最新真实reset+2分钟；唤醒后仍重新读额度，尚未恢复则按最新reset重排，不反复立即唤醒。考虑next_run_at可能相对名义时间提前或延后；本次曾观察提前3分17秒，安排时需另留提前偏移余量并核对实际时间仍>=reset+2min。
- 漏触发时检查last_run及运行记录区分未调度、执行失败与静默完成；保存已证实原因、修复前后实际时间。保证仅限可验证的正确排程，不承诺应用退出/机器睡眠/调度服务故障时仍能送达。不得用常驻进程或未经授权系统定时器掩盖问题。

执行上述核验可使用 `scripts/verify_wake.py`：传本机只读数据库路径、本任务automation-id/thread-id、已向用户告知的expected-nominal、最新reset-at及now（均显式时区）。它检查实际UTC解释与重置后2分钟下限，不负责修改排程，也不证明未来已执行。调度服务的权限/运行记录另外核对。
