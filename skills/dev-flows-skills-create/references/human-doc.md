# 生成 human-doc

为用户、贡献者和维护者建立可查找、可理解且准确的文档指导。名称 human-doc 不代表禁止 agent 读取，而是强调正文读者；不把运行日志、任务清单和决策理由全部塞进用户指南。

## 内容归属与阅读路径

先查现有目录和导航，再决定是否需要调整。区分以下职责：

- 用户指南：完成任务、前提、成本、成功信号、常见失败与恢复。
- 贡献者教程：真实开发入口与可观察验证，按前提组织。
- 架构概览：跨组件关系和扩展点，链接低层契约。
- 包/服务/API 参考：自身契约和限制，不重复别处生成的完整清单。
- 决策与计划：理由和生命周期；未实施计划不能冒充当前能力。
- 复盘与历史：证据和因果；历史格式不能冒充当前运行契约。
- 指令与 skill：流程与行为规则，不是产品事实的唯一归属。

目录结构围绕已有责任，不要求所有项目都建立所有文档种类。教程以结果为路径，参考以查询范围为组织；大段混合时可拆分，小规模混合可明确部分用途。每项事实有一个权威归属，局部安全使用事实可以合理重复。

## 机制准确性

按源代码、配置、manifest、测试与实际操作核验行为。文档指示的非破坏性操作在可用环境中实际运行；密钥、平台或外部状态不可用时准确报告未验证，不填入记忆中的默认值。

安装、启用、挂载、依赖导入与启动可能是不同操作；先按项目事实分类，不从包名称推断。配置的作用域、默认值、失败时点、权限和恢复要保持一致。

代码示例和片段用项目真正存在的检查或可运行场景验证，不凭写了代码块就声称可用。生成目录修改其源头；移动/删除文件同时修复导航和入站引用。

用户内容优先说明能做什么、适用条件与代价；开发者内容解释概念与数据流，精确 API 链接所属参考。保留机制、失败与限制，不为简短抹去条件。不要强制所有文档使用同一 section 名称、fold 或字数预算。

## 按需引入的制度

双语存在时，确认创作侧、术语、结构、确认责任与记录方式。哈希只能固定“曾确认的内容”，不能证明翻译质量。没有双语需求不创建对应文件/sidecar。只有目标确有扩展翻译显式调用政策时才保留该限制。

文档网站存在时，确定编辑源、公开 allowlist、投影/生成和部署是否独立。不能同时维护两套正文，也不能把本地构建称为已发布。没有站点不生成站点规则。

版本与兼容存在时，按真实发布单位定义升级指南与历史记录。记录只描述外部可感知变化及迁移动作；内部全部消费者同步更新不一定需要用户指南。若已经有 ADR 生命周期，引用它；没有但用户授权建立规范时，设计适用的最小政策、实际所属文件、触发和状态变化，明确是本次新规则。只有建议范围时提供方案，不自动建立冻结封存体系。

预算是防止上下文/检索成本失控的工具，不是删减指标。只有已有上限或明确需要时生成预算，先调整归属再精简，额外字数确有用途时允许有依据的调整。

## 支持文件

按实际任务生成最少模板和参考：结构、元数据、风格、审核、网站或翻译等。不创建用不到的空模板；每个模板的 kind/位置/适用条件需明确，不能假设项目已实现模板校验。

指出读取哪个指令/参考的具体路径和触发条件。文档检查映射到真实脚本或明确人工验证，不能为凑流程复制 `doc-sync` 等不存在命令。
