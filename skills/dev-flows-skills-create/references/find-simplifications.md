# 生成 find-simplifications

用于调查、评估或实施有明确范围的简化。description 不应误触发一般功能开发。调查不等于批准所有候选实现。

## 应引导的判断

选择能减少真实维护成本的问题，不以删行数或候选数量为目标：

- 有完整生效路径吗？追踪声明、创建、转换、配置/提供者和最终可观察结果，区别测试描述与生产使用。
- 一个公开区别是否改变消费者行为？内部授权、所有权、驻留或持久性区别可能不可合并，公开冗余区别可另评估。
- 是否可以读取权威源，而不用复制状态、维护缓存或历史？先明确观察时点、延迟和成本，避免删掉实际一致性需求。
- 小而明确的行为能否取代通用机制？说明丢失的能力、现有用户与完整替代成本，不能把行为变化当死代码清理。
- 组合机制是否被误写成业务策略？相似操作的所有权、失败或完成时点是否确实相同？
- 是否只是搬移复杂性？计入胶水代码、配置、测试、依赖、打包、迁移与维护人员成本。
- 外部库是否真正减少自有实现？验证项目特有边界，不重复证明库的全部一般规范。

按项目补充模型/插件动态消费、数据库迁移、前端构建、CLI 安装产物或外部 API 调用路径；不用全部。受保护架构应从项目真实约定得出，不能照搬“两种 LLM 适配器必须保留”等其他项目结论。

## 证据与结果

每个实质候选需要当前所属方、有效生产者/消费者、可删除内容、保留内容、能力损失和最强保留理由。区分不可达清理、明确行为收缩和证据不足。

同进程类型约束、外部 JSON、持久化输入和异步队列的信任/所有权条件不同；不能因防御代码看起来重复而删除。涉及并发、资源或持久化时，追踪取消、重试、回滚、发布时点、清理和兼容数据，保留其实际保证。

受保护义务被破坏、复杂性只是换位置或净收益不足时，拒绝候选。旧否决需要理解仍有效的理由，不能因历史存在就自动否决新的独立项。

小局部清理遵循项目现有任务/注释机制；实质设计提案使用项目现有决策格式。没有该格式时，可建议最小结构：问题、提议、真实备选方案、可观察完成条件、风险与能力取舍。已有同主题所属记录则更新，避免重复。

支持目录变化的项目应说明替代、合并和链接修复机制；没有封存制度不要自建冻结归档。分析输出报告被支持、被拒绝和暂缺证据的项，实际实施才执行适用检查。不要因调查顺带删除记录、关闭 PR 或推进发布。
