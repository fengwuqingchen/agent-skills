# 项目校准与教学深度

本文件用于把发现事实转成能改变后续判断的指导。它不是要求每份 skill 写同样的深度清单。

## 从机制到判断，而非从关键词到目录

只列“检查并发、兼容、性能”不足以教 agent。对于影响项目的关键机制，尽量建立以下可追踪关系：

`项目事实/约定 → 请求或变化触发条件 → 需要追踪的参与者与数据 → 容易混淆的情况 → 保留的保证或放弃的能力 → 所需证据 → 下一动作/停止条件`

不必为每条规则排成七列，也不需要输出推理过程；用一句条件规则、一个边界案例或一个定向参考表达这条关系。重要机制缺证据时说明应读取什么来判断，不把所有内容写成“注意风险”。

例如，存在已发布存储格式时，“检查兼容”可以细化为：同版本写后读取只证明当前往返，不证明历史文件可读；格式变化追踪旧 fixture、加载分发、迁移入口和中断恢复，再由项目承诺选择验证。没有持久化格式的项目不用出现这一条。

## 四种表达强度

创作时按后果、误判概率、恢复难度、项目特有程度、是否易验证和上下文成本，选择表达方式：

| 方式 | 用途 |
|---|---|
| 明确说明 | 高后果、权限、不可逆动作，以及遗漏会使结果无效的不显然约束 |
| 简短提醒 | 常见且影响质量，但 agent 已具备一般技术能力的判断 |
| 结构体现 | 目录归属、模板、实际生成顺序和定向链接能自然表达的常规关系 |
| 省略 | 无关、重复、通用常识或不会改变结果的内容 |

这不是固定打分，也不是限制内容只能四段。少数关键取舍在工作集记录即可，不复制到每份产物。强制语言不能只因“看起来更完整”而增加；项目规则和用户要求的义务强度不得降级。

## 五类 Skill 的实质深度

- 简化：不只寻找可删项，还要求最强保留理由、真实消费者、净维护收益和行为收缩与死代码的区别；说明证据不足时不实施。
- 检查：不只抄命令，还映射变化面、验证入口、能证明/不能证明什么，以及何时旧证据失效；没有可运行检查时给明确缺口。
- 文本：不只“简洁准确”，还说明哪些事实必须局部保留，哪些解释移到所属文档，哪些字符串改变产品行为。
- 文档：不只目录模板，还连接读者任务、前提、成功/失败信号、真实入口、权威来源和下一级细节；支持建立合适的新规范。
- 审核：不只问题清单，还说明怎样追踪真实执行点、独立观察、用户损失和回归证据；区别缺陷、设计分歧和未验证。

用户选择只生成一类时，深度集中于该类，不能把其他四类的全部职责拼进去。

## 同一原则在不同项目中的变化

| 示例项目 | 有依据时需要加深的判断 | 通常不应引入的制度 |
|---|---|---|
| 小型离线 CLI | 已发布文件格式、错误码、安装入口和临时数据验证 | 托管 PR、全平台矩阵、多语言配对 |
| 多租户服务 | 租户与授权沿入口到执行、事务/重试、旧客户端和部署顺序 | 没有实际需求的插件加载、模型快照 |
| 公共库 | export、真实外部消费者、构建产物、版本和弃用承诺 | 应用 UI 字典或部署操作 |
| 前端产品 | 路由、构建/生成、异步界面状态、可访问性和实际浏览器证据 | 没有服务端数据时的数据库迁移体系 |
| 资源受限或系统软件 | 资源上限、进程/内存所有权、平台 ABI 和真实硬件证据限制 | 只有 Web 项目适用的检查命令 |

这些是校准例子，不是预设架构。混合项目按真实职责合并，不要求套一个分类。

## 可接受的完成状态

后续 agent 应能在单独读该 skill 后，知道从哪些实际文件取得证据、什么情况改变选择、产出什么，以及何时停止。若去掉项目名后内容几乎对任意仓库都相同，继续加入有证据的项目机制；若内容只是逐项罗列不存在的机制，删掉它们。短而判别性强的指导可以完成；长而没有这些关系的指导需要重写。
