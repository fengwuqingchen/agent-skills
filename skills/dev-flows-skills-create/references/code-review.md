# 生成 code-review

用于审核目标项目变更，不自动执行修复、评论、批准或合并。用户授权修复或发送 review 时才进入相应动作。输出是指导与真实关注点，不是每个 PR 都遍历的安全大全。

## 先定位审核对象

确认用户给出的文件、工作树、commit、PR 或 branch 以及实际基线。只读检查 dirty 修改，避免把基线外变更混入判断。remote 不可用时报告本地基线限制，不能捏造已 fetch。非 Git 项目可以按实际交付版本比较。

引用已有架构、测试与决策规范。不同意某 ADR 是设计讨论，不能自动当成实现缺陷。优先真实正确性、安全、生命周期和必需行为，少量有证据问题优于大量风格意见。

## 选择相关审核角度

| 角度 | 需要追踪的事实 |
|---|---|
| 意图与消费者 | 声明变化与实现一致吗，真实用户/调用者是否受影响 |
| 接口与兼容 | 输入、返回、错误、协议、配置、公开入口与旧消费者 |
| 生命周期与并发 | 发布、重入、await、取消、重试、资源和清理顺序 |
| 状态与权威 | 借用/拥有值、派生缓存、通知时点、回放与查询来源 |
| 数据与恢复 | 事务、迁移、持久化、旧数据、失败后恢复和回滚边界 |
| 执行约束 | 授权/限制是否在实际执行处成立，替代入口是否可绕过 |
| 边界与性能 | 完整输出而非中间结果的限制，编码、批量、尾延迟与成本 |
| 架构与必要性 | 新抽象是否服务现有消费者，是否不必要扩张公共 API |
| 配置与产品行为 | 默认选择的证据、模型/UI/CLI 可见文字和本地化 |
| 入口与产物 | 真正发布的服务、Loader、bin、worker、安装或打包路径 |
| 测试 | 能否在目标回归失败，独立观察、负对照、恢复、可靠性 |
| 文档与决策 | 代码变化同步当前契约，落地提案改为已实现事实 |

不让框架特有 export 规则、插件 disposer、模型快照、本地化字典或不变量伴随模块变成所有项目必须采用的技术。机制确实存在才写其义务和路径。若项目有独立观察的不变量检查，要审核真实关系，不能用同次操作自我验证冒充独立证据。

自动检查只证明其覆盖规则，不能证明设计、事实和翻译质量；测试覆盖率也不证明断言场景正确。复核作者声称的检查与实际范围，不无理由重跑整个套件。

## 结论与动作

每个发现给出位置、触发情形、影响和证据；不确定问题标明不确定，不捏造严重级别。区分阻塞、建议和缺少验证，避免重复已由检查发现且修复的问题。

局部缺陷定位到最窄代码范围，跨模块问题给整体说明。用户只请求本地审核时只在当前交付中报告，不调用外部评论工具。用户明确授权外部 review 时遵循项目已有渠道，不另造重复线程。

处理 review 意见时逐条验证并基于事实修复或反驳，不能因评审者提出就无条件接受。批准、合并、关闭或重写其他工作需要对应授权，不能由审核 skill 赋予。
