# 验证与行为试用

## 静态与事实验证

对生成的每份 skill 检查名称、前置元数据、description 的触发边界和未完成脚手架；有可用 skill-creator 时运行其 quick_validate.py。不要把格式通过称为语义正确。

跟随所有本地链接，确认指令、参考、模板和命令入口真实存在；相对路径按输出实际位置解析。查找残留 `<project>`、`{{project}}`、旧仓库前缀和私人绝对路径，但根据上下文判断合法语法示例，不机械删除所有尖括号。

逐条核对关键机制：

- 来源是现有项目规则、用户要求还是建议，是否被写错强度？
- 消费者、数据格式、发布方式、测试范围和入口是否有依据？
- 没有双语、归档、插件或 PR stack 时是否仍强加这些要求？
- 引用的其他 skill 在目标环境存在吗？是否保持独立可用？
- 调查是否误授予写入，审核是否误授予外部评论，检查是否误授予 push？
- 普通工作是否被迫启动全库审计、全面测试或固定多 agent 流程？
- 未运行命令是否明确区分，是否声称已接入 CI/自动加载？
- 每份是否有有效结果、普通停止点和缺证据处理，子集生成是否仍独立可用？
- 请求读取辅助规则是否被写成无条件启动别的工作流，是否会递归扩大范围？
- 关键项目机制是否连接了触发、取舍与证据，而不是只罗列“注意兼容/性能”？
- 用户要求建立新规范时是否实际提供适用规则，而不是仅说原来不存在？

新脚本用真实有效和无效输入测试，核对输出和副作用；不要只测试生成文案的标题/正则。未新增脚本不需要人为创建测试框架。

## 行为试用

重要生成结果可在隔离 workspace 进行独立试用。给评估者 skill、实际用户请求与必要原始项目文件，不传入预期答案或先前结论。明确禁止 push、网络写入、生产迁移和未授权项目外修改。

按实际生成职责选择一个或少量高价值情形，不要求固定全矩阵：

- 只有小型本地 CLI、单语、没有 PR 的项目，生成能否保持轻量？
- 有已发布库 API 和旧数据，能否保留外部兼容义务？
- 有现有 ADR/文档权威，能否沿用并避免竞争规范？
- 只请求审核或简化调查，能否限制为发现而不执行变更？
- 缺少某项执行环境，能否报告未验证而不捏造检查通过？
- 只生成 human-doc 或 code-review 时，是否不链接缺失的同组 skill？
- 单独调用生成 skill 后，是否完成原请求并停止，而非触发整组完整流程？

观察产物和行为而非自述：skill 是否项目专属，引用可解析，机制没有错植，命令确有入口，授权范围保持正确。只有观察到的问题才支持修改，不能因评估者偏好增加普遍要求。

没有独立评估条件时，自己从请求追踪加载文件、行动和证据，报告未进行独立行为测试。受限验证不妨碍交付已经正确完成的文件，但不能把受限结果称为全面验证。
